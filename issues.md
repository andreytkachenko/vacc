## 1. Library-user perspective (public API)

### 1.1 The frame types are the weakest public surface
- **`PixelData.format: String`** (`vacc-core/src/frame.rs:261`): stringly-typed pixel format, heap-allocated on *every* frame by every backend (`src/decoder.rs:246`, `src/transform.rs:109,269`, NVDEC/VAAPI equivalents). Should be a `Copy` enum (`I420 | NV12 | P010 | I420_10 | …`) with `Display`. This is both a per-frame allocation and an API footgun (typo-prone matching in user code, e.g. the facade's own `map_source` matches on `"I420"`, `"P010"`, `"Y410P16"` — `src/transform.rs:159-185`).
- **Raw pointers in `PixelPlane`** (`frame.rs:217-227`): users must hand-write `unsafe { from_raw_parts(p.data, p.height * p.pitch) }` to read a plane (the facade does exactly this in `src/transform.rs:326-328`). Add safe accessors: `impl PixelData { fn y(&self) -> &[u8]; fn u(&self) -> &[u8]; fn v(&self) -> Option<&[u8]> }` computed from `buffer`. The manual `Clone` rebase (`frame.rs:272-298`) shows how fragile this is; a view API would remove the whole class of lifetime bugs for embedders.
- **PTS units are inconsistent**: `DecodedFrame.timestamp` doc says "nanoseconds, or codec-specific units" (`frame.rs:8`), the facade synthesizes in microseconds with a 1/30 s step (`src/decoder.rs:367`), `EncodedFrame.timestamp` says nanoseconds (`vacc-core/encoder.rs:164`). Pick one (microseconds is the de-facto standard), state it once, and have backends emit it.
- **Two overlapping device-frame APIs**: legacy `device_ptr`/`device_copy_event`/`device_seq` raw-pointer fields (`frame.rs:33-50`) next to the newer `gpu: Option<GpuFrame>` (`frame.rs:59`). The legacy trio is only fed by NVDEC's `set_device_output_ring`; it should be deprecated in favor of `GpuFrame` (which already models copy-done fences and consume barriers).
- **`unsafe impl Send + Sync for DecodedFrame`** (`frame.rs:66-67`) is justified, but the justification depends on user discipline around the raw-pointer fields — another argument for hiding them.

### 1.2 Facade (root `vacc` crate)
- **`Decoder::new(Vec<u8>)` / `new_with_format` contradict the documented "streaming-only" contract** (`src/lib.rs:11-17`). The trait takes whole-stream constructors, `VaccDecoder::new_with_format` always returns an error, and `new(data)` just forwards to `new_auto`. Either implement them or mark the trait methods as backend-specific with docs.
- **Error model is lossy**: `UnifiedError::Backend { source: Box<dyn Error> }` (`src/error.rs:50-51`) means users can't match on *why* a backend failed (device lost vs corrupt stream vs OOM) — they get a string. `BackendFailure.message: String` likewise discards types at init time. Add a machine-readable code (e.g. `enum UnifiedErrorKind { Init, Decode, DeviceLost, Oom, Unsupported, … }`) alongside the string.
- **Duplicated facade glue**: the `be()` helper, the backend-dedup loop (`seen: [bool; 4]`), and the `catch_unwind` fallback loop are copy-pasted between `src/decoder.rs:33-35,397-432` and `src/encoder.rs:20-22,71-98`. A shared `try_backends(order, create)` helper would cut ~60 lines and keep the two in sync.
- **`DecoderConfig::with_gpu()` doc is stale**: says "backend is forced to Nvdec" but the code filters the order to Vulkan∪Nvdec (`src/config.rs:54-57` vs `src/decoder.rs:380-392`).
- **lib.rs capability table is wrong** (`src/lib.rs:78-85`): Vulkan encode and NVENC encode both exist and work (H.264, CQP, I/P only — see §2); the table says "planned". Users reading the docs will avoid working backends.
- **Vulkan is a second-class citizen by design**: whole-stream buffering + all-frames-retained (`src/decoder.rs:89-97,136-155`), double device/session creation per stream (validation decoder built and dropped at `src/decoder.rs:119-134`, then rebuilt in `start()`), and `reset()` that bricks the adapter (#4). The inner crate *does* have a bounded-output `decode_stream(max, emit)` (`vacc-vulkan/src/decoder.rs:686-697`) that the facade never uses — wiring `submit` to append+extract (the parser is already stateful) would make Vulkan a proper streaming backend and remove the memory cliff.
- **`VaccEncoder::new` doesn't pre-validate**: each backend calls `config.validate()` itself, so an invalid config surfaces as per-backend failures in `AllBackendsFailed` rather than one clean `InvalidConfig` error. Validate once in the facade.

### 1.3 Backend-crate public surfaces
- **Software decode has two different error types** (`vacc-software-decode/lib.rs:20` exports HEVC's 5-variant `Error`; `SwH264Decoder::Error` is a *different* 6-variant enum, `decoder.rs:77-92`). An embedder writing generic code can't represent both. Also `SwH264Decoder` is `Send` but not `Sync` (a `RefCell` mb-dump field), `SoftwareH265Decoder` effectively is — asymmetric for thread pools. Test-only API (`arm_mb_dump`/`take_rust_records`) is public.
- **NVDEC exposes raw CUDA handles** (`set_device_output(CUdeviceptr)`, `set_device_output_ring(&[CUdeviceptr])`, `slot_waits: &[Vec<*const c_void>]`, `nvdec-decode/decoder.rs:410-458`) with no RAII, while the higher-level `GpuFrame`/`DeviceRing` abstractions exist in the same crate — the raw overloads should go behind a feature or be removed. No SDK/driver version negotiation for `libnvcuvid.so` (silent ABI drift risk), and the library search path includes the CUDA **stubs** dir (`device.rs:642`) which loads fine and fails confusingly later. Doc comment says the H.264 decoder is "not Send/Sync" while it has `unsafe impl Send`.
- **`vacc-vulkan-decode`'s `Decoder` trait impl is a stub** (`submit`/`decode` return "not supported — use decode_all", `flush` empty, `reset` no-op, `info()` hardcoded wrong data, `decoder.rs:72-120`) — the wrapper advertises an API it doesn't provide.
- **VAAPI capability query lies by omission**: `query_capabilities` ignores its chroma/bit-depth args and hardcodes 4:2:0 8/10-bit, 4096×2160, 16 slots (`vaapi-decode/device.rs:124-158`) even though the decoder supports 4:2:2/4:4:4/12-bit.
- **`vacc-image` API gaps**: 4:2:0 only (`pixel.rs:119-121` hardcodes `w/2` chroma), no crop/source-rect, `ColorSpec::auto(height)` is a height heuristic that always assumes Limited range (`spec.rs:61-70`) with no VUI-driven selection at the facade, `Kernel` not exposed (facade always passes `Auto`), and `warp_rgb` has no `Kernel` parameter at all. Same `ImageConfig` yields *different behavior per backend* for Box/Bicubic (NPP maps Box→linear, vkimage rejects non-bilinear) — document or unify.

## 2. Undone / incomplete

**Decode:**
- **Software**: no VP9/AV1 (known). H.264 10-bit / 4:2:2 / 4:4:4 / interlaced are *rejected* (good, with errors) — but HEVC 4:2:2/4:4:4 is *silently misdecoded* (#7). `new_with_format` unimplemented on both sw decoders. H.264 `adaptive_ref_pic_marking_mode_flag`: parsed and honored by all GPU backends, but the SW decoder derives MMCO-vs-sliding-window from `!mmco_commands.is_empty()` (`sw decoder.rs:579`) — wrong for flag=1 with zero MMCO ops.
- **Vulkan**: interlaced H.264 impossible (`PROGRESSIVE` hardcoded ×3: `device.rs:825`, `profile_chain.rs:228`, `decoder.rs:906,4298`); film grain disabled (`decoder.rs:4322`); AV1 temporal layers unfiltered (all TIDs decoded, `access_unit.rs:1493-1529`); H.264 long-term refs unimplemented (#6); no `reset` API in the inner decoder at all; HRD params skipped (`h264.rs:958`).
- **NVDEC**: AV1 film grain parsed but `apply_grain` forced 0 (`av1.rs:335-338`); AV1 temporal layers not skipped; H.264 picparams "EXPERIMENT" fields are wrong — `pic_order_present_flag` mapped from the *wrong PPS field* and ref-idx actives taken from PPS defaults instead of slice-resolved values (`picparams.rs:92-96`) → wrong prediction lists whenever a slice overrides; interlaced frames decode but output metadata lies (`progressive_frame=1` hardcoded, `decoder.rs:1820-1832`).
- **VAAPI**: H.264 High 4:2:2 (profile 122/244) mapped to `VAProfileH264High` with YUV422 format — likely rejected/mis-decoded (`decoder.rs:3754-3785`); the 10-bit fallback ladder lists only 8-bit profiles; AV1 restricted to VA profiles 0/1; `decode()` has a placeholder-frame fallback for unhandled codecs that **clears all pending input** (silent data loss, `decoder.rs:1702-1713`).
- **Parser**: no AV1 superframe support (`ObuType` has no superframe variant, `av1.rs:44-59`) while lib.rs:9 doc *claims* "VP9 superframe support" (doc/impl mismatch — neither exists in the parser; backends do their own expansion); `read_uvlc` silently saturates to `u32::MAX` on ≥32 zeros (`bitreader.rs:169-171`); H.264 POC type-2 wrap detection is naive (`h264_poc.rs:232`).

**Encode:**
- All four encode backends are **H.264-only, 8-bit, CQP-capable but minimal**: Vulkan (I/P only, no B-frames, synchronous), NVENC (CQP forced, `frameIntervalP=1` → I/P only), VAAPI (Main profile + level 3.1 hardcoded, `max_num_ref_frames=1`, CAVLC, no weighting, ~10 VA buffers created/destroyed per picture). The software encoder is the most complete (real ME with hexagon+diamond+subpel SATD, CABAC+CAVLC, CRF/ABR-VBV/2-pass VBR, B-frames 0–3) but: 8-bit only (`nal.rs:57-58`), weighted prediction always off, naive B-frame reference selection (`lib.rs:671-687`), and zero tests in `slice.rs`, `ratecontrol.rs`, `nal.rs`, `picture.rs`, `lookahead.rs`, `deblock.rs`, `cabac_mb.rs` — the hand-rolled CABAC bin sequencing has only 1 unit test.
- README "HEVC encode planned" is accurate; lib.rs table is not (#19).

**Image pipeline:**
- NPP `warp_rgb` is a public landmine + dead warp arms in `process()` (#16); vkimage is bilinear-only and even-dimensions-only (`lib.rs:594-603,1137-1164`); no crop; 4:2:0 only.

## 3. Hot-path optimizations (ranked by expected impact)

**A. GPU backends — synchronization is the dominant cost, not CPU work.**
1. **Vulkan decode pipeline** (#10): replace the 2-submits/2-blocking-waits/single-fence design with a small ring of (CB, staging buffer, fence) triples so decode N+1 overlaps readback N; pool primary CBs (allocated per frame today, `decoder.rs:3136` etc.); batch or remove the per-frame `vkFlushMappedMemoryRanges` whose error is swallowed (`decoder.rs:962`). Also **read the inline query results** or delete the query machinery entirely.
2. **NVDEC HEVC/VP9/AV1 full-context syncs** (#11): adopt H.264's targeted `cuvidGetDecodeStatus` busy-poll for all four codecs; on the GPU track, use the existing `DeviceRing` instead of per-frame `cuMemAlloc`/`cu_ctx_synchronize` (`gpu.rs:45,103`).
3. **VAAPI readback** (#6 in that report): stop doing `data.to_vec()` of the *entire* mapped image (full coded size with pitch padding, `decoder.rs:3269`) — copy only the crop region into a pooled tight buffer; the packed-format software unpack loops (`decoder.rs:3105-3211`) should be SIMD'd.
4. **NVDEC readback**: 5 per-frame heap allocs + byte-wise NV12 de-interleave after two synchronous `cuMemcpy2D` (`decoder.rs:1594-1670`) — pool the output planes and SIMD the de-interleave (it's a trivial shuffle).

**B. Software decode.**
5. **Pool HEVC per-picture scratch** (#12): move the grid set, SAO orig-copy buffer, and TU temporaries into the decoder struct / `thread_local` (a `TU_SCRATCH` already exists at `coding_tree.rs:1925` but isn't used by `inverse_transform_2d`). Eliminates ~30 MB/frame of alloc churn at 4K.
6. **SIMD the remaining scalar kernels**: HEVC deblock (`deblocking.rs:489-815`), SAO (`sao.rs:123+`), `reconstruct_block` (bounds check in the innermost loop, `coding_tree.rs:651-659` — split interior/edge), and **AVC intra prediction** (`avc/intra.rs` is a *scalar re-expression of C SSE kernels* — per-lane byte math emulating intrinsics; no real SIMD anywhere in the file).
7. **Kill per-slice bitstream copies**: HEVC `slices.clone()` deep-clones every NAL payload per decode (`h265.rs:557`) on top of a full RBSP copy per slice segment (`driver.rs:244`); AVC clones each NAL + allocates a guarded buffer (`decoder.rs:721-726`). Borrow from the packet or share via `Arc`.
8. **Remove the MC read-back round-trip**: PU-level MC writes prediction into the picture, then the TU decoder reads it back and writes it again (`coding_tree.rs:1640, 2059-2063, 2178-2183`) — double plane traffic for every inter TU.
9. **Stop deep-cloning `last_emitted_pic`** per emitted frame (`h265.rs:665`, ~56 MB @4K) — keep a slot index/generation.
10. **AVC is single-threaded** while HEVC WPP uses rayon; AVC multi-slice could parallelize over slices the same way.

**C. Software encode.**
11. **Reuse the decoder's SIMD kernels** (#13): SAD/SATD and MC dominate ME cost; the decoder already has SSE4.1 MC/IDCT/deblock. Create a shared `vacc-dsp` crate (or an encoder→decoder dependency — no cycle today) and port `dsp.rs`, `transform.rs`, `intra.rs`. Also replace per-candidate `Box<Cand>` (~384 B, multiple per MB in P/B modes, `slice.rs:141-145`) with a thread-local pool.

**D. Image pipeline.**
12. **AVX2 H-pass for ch=1/ch=3** (#14): today only RGBA32 resizes are SIMD'd on the H-pass; add ch=1/3 kernels and an AVX2 V-pass (the SSE4 V-pass exists). Hoist the per-row kernel dispatch in `convert_rows` (`conv.rs:305-318,335-346`) and warp's per-row interpolation match to once-per-call (resize already does this).
13. **Fuse the 10-bit downcast into the H-pass** instead of materializing a full-frame I420 intermediate (`pipeline.rs:209-223`).
14. **NPP host path**: 3–4 serialized `cuStreamSynchronize` + 6–9 `cudaMalloc`/free + H2D/D2H per frame (`lib.rs:1072-1122`) — likely *slower* than the SIMD CPU pipeline for typical frames; batch planes into one submit or skip NPP for host-resident frames. Cache tap coefficients keyed on `(filter, src, dst)` across frames (small win, `resize.rs:154-181`).
15. **vkimage host path**: two full-frame scalar passes (u8→u32 expansion on upload, word→byte repack on readback) = 4× frame memory traffic on CPU (`lib.rs:205-233,855-913`).

**E. Micro.**
16. `to_core_frame` (Vulkan facade): replace `chunks_exact(row_stride).nth(top + r)` per row with direct slice indexing — O(rows²) → O(rows) (~7M iterator steps/frame @4K, `src/decoder.rs:219-226`).
17. `normalize_u16_to_top` (facade, 10-bit sources): scalar per-pixel `u16::from_le_bytes` loop, trivially SIMD-able (`src/transform.rs:210-227`).
18. Remove the 3 unconditional `eprintln!`s in sw HEVC (#2) and the ungated debug prints in `vacc-vulkan` (169 in `decoder.rs`, MMCO prints unconditional in `dpb.rs:135-144`) — stderr I/O on the hot path.

## 5. DRY / commonization opportunities (ranked by drift risk)

1. **H.264 DPB ×3** — the highest-risk duplication: NVDEC's private 1353-line `NvdecDpbManager` (spec-correct MMCO 1–9 incl. LT refs), the shared `vacc-parser/h264_dpb.rs` (LT ops no-op'd, non-spec op numbering in docs), and Vulkan's own (`dpb.rs:92-138` + explicit branch at `decoder.rs:1157-1167`). The drift already produced the VAAPI bug (#5). **Action:** make NVDEC's spec-correct MMCO handling the shared implementation in `vacc-parser`; VAAPI already consumes it — port Vulkan and NVDEC, delete ~2.5k lines.
2. **IVF parsing ×4 + duplicated `detect_codec`** — facade (`src/codec.rs:10-13`), VAAPI (`decoder.rs:516` + a *full copy* of detect at `decoder.rs:3600-3640`), Vulkan (`access_unit.rs:1209-1265`), NVDEC AV1 (`av1.rs:696-706`). Offsets are verified canonical (checked against real FFmpeg output), so unification into `vacc-parser` is behavior-neutral. Also move the single source of truth for codec detection there and fix the raw-AV1-OBU bug once.
3. **NVDEC `extract_frame` ×4** — ~1k lines of copy-pasted map→pinned-cache→2×`cuMemcpy2D`→unmap→de-interleave→build-frame across `decoder.rs:1226-1707`, `h265.rs:949-1349`, `vp9.rs:863-1190`, `av1.rs:1248-1573`; P016 handling already diverges between copies. One shared `extract_surface()` helper parameterized by format/bps.
4. **Superframe/AV1 OBU expansion ×2** — `expand_superframes` (`vp9.rs:259-336` vs `vaapi-decode/decoder.rs:4421-4491`), `av1_extract_frame_obus` / `find_sps_obu` (same pair pattern) — move to `vacc-parser` where the OBU types live.
5. **NAL extraction near-copies** — `h264.rs:1261` vs `h265.rs:2144` (39/38 lines, identical start-code scan) + the NAL-cache/truncation-holdback pattern duplicated (`h264.rs:39-49` vs `h265.rs:2242-2255`). One parameterized extractor with a header-parse closure.
6. **Bit readers ×3** — `vacc-parser/bitreader.rs` (byte-state machine; `ue()` scans leading zeros one bit at a time via full `read_bits(1)` calls — a 64-bit word cache would speed header parsing noticeably), sw-HEVC's own reader (`hevc/bitreader.rs:81,131` — justified by CABAC batching, document it), and Vulkan's third private `SliceBitReader` with `unwrap_or(0)` defaults (`access_unit.rs:152-209`) that double-parses H.265 slice headers (once privately, once via the shared parser per call).
7. **Dead code to delete** — entire `vacc-vulkan-common` crate (485 lines; a second device-creation path nothing depends on), `vacc-vulkan/pipeline.rs` (608), `vacc-vulkan/frame.rs` (160), `BitstreamStream` (`vacc-parser/bitstream.rs:198`, no consumers), `is_av1` heuristic (`av1.rs:2518`, never called, nonsensical).
8. **Encode helper duplication** — `vacc-vulkan-encode` re-implements `find_memory_type/alloc_memory/bind_video_memories/create_video_image/create_host_buffer` (`session.rs:129-295`) instead of reusing `vacc-vulkan` helpers; NVENC and VAAPI encoders each re-implement pitched-packing/upload with no shared helper.
9. **avc ↔ hevc (sw decode)** — the divergence is mostly *justified* (different algorithms, bit-exact golden ports; `vacc-common` docs record this decision), but: median-of-3 / MV clipping / distance-scaling could share a small generic core; weighted-prediction both end in the same per-sample `clip((p·wq+q·wp+oy) >> wd)` — one shared kernel; BETA/TC tables are near-copies (`avc/deblock.rs:1418-1432` vs `hevc/deblocking.rs:20-38`). Inside crates: HEVC L0/L1 blocks are ~60-line near-copies (`inter_prediction.rs:1064-1181`); AVC's five `inter_*` sub-partition functions are near-identical (`mvpred.rs:359-572`).
10. **Resize re-derived ×3 with different semantics** — reference (Mitchell cubic + box coverage + exact-even-ratio fallback that works around nppiResize 2× degeneration, `resize.rs:60-76`), NPP (native `nppiResize`, documented deviations up to ~170 max on HF content), vkimage (own WGSL bilinear). Share the tap-table builder or add cross-backend golden tests so drift is caught, not discovered.
11. **`vacc-core` hygiene** — Vulkan-specific types (`session.rs`: `VideoSessionParams`, `VideoDecodeInfo`, `VkVideoFormat`…) leak `ash` into a backend-agnostic core; `BitstreamBufferDescriptor` is dead; `VideoCodec` conflates decode/encode variants with flag-bit discriminants and inconsistent `name()` ("h264" vs "encode_h264").

## 6. Suggested sequencing

1. **Week 1 (correctness, low risk):** remove the 3 sw-HEVC `eprintln!`s; fix `detect_codec` raw-AV1; reject HEVC 4:2:2/4:4:4 in sw; fix VAAPI MMCO mapping + LT no-ops (or route VAAPI H.264 through NVDEC's spec-correct logic); make Vulkan `reset()` work (rebuild adapter) or return a clear error; convert `avc/slice.rs:488` debug_assert and HEVC `expect()`s to `Err`; fix `has_more_rsbp_data`.
2. **Week 2 (perf, high impact):** Vulkan fence/CB/staging rings + read-or-delete query pool; NVDEC per-codec targeted status poll + DPB entry trimming; sw-HEVC scratch pooling; kill `last_emitted_pic` clone and per-slice NAL clones; fix the Vulkan `Box::leak`s (memory leak).
3. **Week 3+ (API + DRY):** `PixelFormat` enum + safe plane accessors in `vacc-core`; unified PTS unit + backend PTS emission; error-kind codes; shared H.264 DPB across NVDEC/Vulkan; IVF + codec-detection centralization; shared `extract_surface` in NVDEC; delete dead crates/files; encoder SIMD via shared dsp crate.

**What's genuinely good** (for balance): the streaming parser design with `TRUNCATED_TAIL` is consistent end-to-end across all backends; AVC per-MB decode is allocation-free with a well-designed slot pool; HEVC WPP uses rayon; the GPU-track `GpuFrame`/`GpuEvent` abstraction is sound (RAII ownership, reader barriers); NPP/vkimage/CPU share the Q14 conv tables and vkimage's resize matches the CPU reference bit-for-bit; golden-test coverage across all decoders is extensive; no `todo!()`/`unimplemented!()` anywhere in production code.
